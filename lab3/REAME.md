# 1. Выбор архитектуры приложения
На основе анализа предметной области (управление номерным фондом гостиницы), выделенных сценариев использования и требований к системе выбрана трёхуровневая архитектура веб-приложения.

Тип приложения: веб-приложение (клиент-серверное).

Основные уровни архитектуры:

Уровень	Назначение
Frontend (клиентская часть)	Предоставление пользовательского интерфейса для администратора, гостя и персонала. Отображение каталога номеров, форм бронирования, календаря загрузки, списков уборки. Взаимодействие с сервером через HTTP/REST API.
Backend (серверная часть)	Обработка бизнес-логики: проверка доступности номеров, расчёт стоимости, создание и отмена броней, заселение/выселение, аутентификация и авторизация, отправка уведомлений.
Database (база данных)	Постоянное хранение данных о номерах, категориях, тарифах, гостях, бронированиях, проживаниях, пользователях.
Преимущества выбранного подхода:

каждый уровень можно разрабатывать, тестировать и масштабировать независимо;

чёткое разделение ответственности между компонентами;

возможность замены одного уровня без влияния на другие (например, смена СУБД или фронтенд-фреймворка);

упрощение поддержки и сопровождения системы.

# 2. Определение компонентов системы
## Frontend (клиентская часть)
Компонент	Назначение и ответственность
Веб-интерфейс администратора	Поиск свободных номеров, оформление броней, заселение, выселение, управление статусами номеров, регистрация гостей, просмотр календаря загрузки.
Веб-интерфейс гостя	Регистрация, просмотр каталога номеров и цен, создание брони, отмена брони, просмотр истории бронирований.
Веб-интерфейс персонала (горничных)	Просмотр списка номеров, требующих уборки, отметка номера как готового к заселению.
Модуль аутентификации (клиентский)	Формы входа, регистрации, восстановления доступа; хранение токена сессии.
## Backend (серверная часть)
Компонент	Назначение и ответственность
Контроллеры	Приём HTTP-запросов от Frontend, валидация входных данных, вызов соответствующих сервисов, формирование HTTP-ответов.
Сервисы Бизнес-логика: проверка доступности номера на даты, расчёт стоимости проживания, создание/отмена брони, заселение/выселение, проверка дубликатов гостей, управление статусами номеров.
Репозитории	Доступ к данным: SQL-запросы к базе данных для чтения и записи информации о номерах, гостях, бронированиях, проживаниях.
Модели Описание структуры данных предметной области: Номер, Категория, Гость, Бронирование, Проживание, Пользователь.
Модуль аутентификации и авторизации	Проверка учётных данных, выдача токенов, разграничение прав доступа по ролям (администратор, гость, персонал).
Модуль уведомлений	Формирование и отправка email/SMS-уведомлений о подтверждении брони, отмене, заселении.
Модуль фоновых задач	Асинхронная обработка длительных операций: массовая рассылка уведомлений, формирование отчётов.
## База данных
Компонент	Назначение и ответственность
Хранилище данных	Таблицы: номера, категории, гости, бронирования, заселено, пользователи, права доступа, уведомления.
СУБД	PostgreSQL (реляционная база данных).
## Внешние сервисы
Компонент	Назначение
Email/SMS-шлюз	Отправка уведомлений гостям и персоналу.
Сервис аутентификации (внешний)

# 3. Проектирование взаимодействия компонентов
## Общая схема взаимодействия
Пользователь (Администратор, Гость, Персонал) взаимодействует с Frontend через веб-браузер.

Frontend отправляет HTTP/REST-запросы к Backend.

Backend проверяет права доступа через модуль аутентификации.

Контроллер принимает запрос и передаёт управление соответствующему сервису.

Сервис выполняет бизнес-логику и обращается к репозиторию.

Репозиторий выполняет SQL-запросы к базе данных.

При необходимости сервис инициирует отправку уведомления через модуль уведомлений и внешний Email/SMS-шлюз.

Результат возвращается по цепочке: База данных → Репозиторий → Сервис → Контроллер → Frontend → Пользователь.

## 4. Индивидуальная особенность предметной области
## Описание особенности
Особенность: автоматическая проверка занятости номера на конкретные даты «на лету» для исключения двойных бронирований.

В чём заключается: при создании бронирования система в реальном времени анализирует все существующие брони и проживания для выбранного номера и проверяет, не пересекаются ли даты нового бронирования с уже занятыми периодами. Если пересечение обнаружено — бронирование отклоняется с предложением выбрать другой номер или даты.

Почему это важно для гостиничного предприятия: двойное бронирование — одна из ключевых проблем, указанных в описании предметной области. Ручной учёт в журналах и электронных таблицах не позволяет гарантировать отсутствие накладок. Автоматическая проверка занятости исключает человеческий фактор и повышает качество обслуживания.
